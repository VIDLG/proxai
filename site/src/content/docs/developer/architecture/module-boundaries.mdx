# Module Boundaries

This page is a maintainer map for deciding where code belongs. When in doubt, keep protocol conversion explicit and keep provider-specific behavior out of generic translation.

<ProxaiCallout type="caution" title="Do not blur protocol and provider boundaries">
  Provider names are user labels. Protocol names describe wire behavior. A provider module may adapt local provider quirks, but general protocol-to-protocol shape changes belong in `crates/proxai-core/src/translation/`.
</ProxaiCallout>

## Observation and logging boundary

`proxai-core` defines the shared `Observer` contract, closed `Observation` variants, and a no-op default. Core ingress, provider normalization, and translation emit typed variants through that contract. They do not select `tracing`, diagnostics files, capture storage, metrics backends, or any other concrete sink; the downstream application composes those implementations.

For request-scoped code, emit stable lifecycle and domain events through `ObserveContext`. `ObserveSinks` then decides whether each point goes to logging, diagnostics, capture, or several sinks. The logging sink is the layer that translates an observation into a `tracing` event and chooses its level and output format.

  columns={['Situation', 'Use']}
  rows={[
    ['Core legal-but-lossy adaptation or ingress compatibility event', 'A typed `Observation` variant through the shared `Observer`; the downstream decides the sink.'],

    ['Logging sink implementation', 'Direct `tracing`; this is where level and formatting are selected.'],
